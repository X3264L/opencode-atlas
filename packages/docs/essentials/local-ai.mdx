OpenCode can run coding agents against local models on your own machine. Open `/local` in the TUI to see which runtimes are running, what your hardware can handle, install recommended quantizations, and switch to a local model.

## Supported runtimes

| Runtime | Discovery | List | Install/Remove | Streaming | Benchmark | Readiness |
| --- | --- | --- | --- | --- | --- | --- |
| Ollama | Full | Full | Full (Atlas-managed pull) | Full | Full | Full |
| LM Studio | Full | Full | External (managed in the LM Studio app) | Full | Full | Where supported |
| llama.cpp | Server discovery | Full | External (GGUF file required) | Full | Full | Where supported |
| MLX | Apple Silicon only | Full | External (Hugging Face cache) | Full | Full | Where supported |

Notes:

- **Ollama** is the reference runtime and the only one with full Atlas-managed lifecycle for registry pulls today.
- **LM Studio**: Atlas detects a running server (default `http://127.0.0.1:1234`, override with `LMSTUDIO_HOST`) and can use every exposed model for inference, benchmarks and readiness. Model downloads stay inside the LM Studio app - Atlas does not fake install buttons.
- **llama.cpp**: two modes.
  - *External*: Atlas targets an already-running `llama-server` (default `http://127.0.0.1:8080`, override with `LLAMACPP_HOST`).
  - *Atlas-managed*: you register a local `.gguf` file in `/local`, point Atlas at your `llama-server` executable once, and Atlas owns the process lifecycle - launch on a free loopback port, health-gated startup, stop/restart, bounded log capture, and cleanup on normal OpenCode shutdown. See [Managed llama.cpp](#managed-llamacpp).
  - GGUF filenames are parsed for quantization labels (e.g. `-q6_k`) so identities stay meaningful.
- **MLX**: requires macOS on Apple Silicon; on any other platform it reports "unsupported" and is never probed as a backend. Point it at an MLX server (`MLX_HOST`, default port 8080). Recommendations still use unified-memory awareness from shared hardware detection.

## Managed llama.cpp

For GGUF users who do not want to touch a terminal:

```text
/local → Import GGUF → path → Start
```

How it works:

1. **Register** - Atlas validates the file exists, is a regular `.gguf`, and derives identity from the filename when confident (`Qwen3-Coder-30B-Q6_K.gguf` → family/size/Q6_K). Unknown models stay "Unknown GGUF model". The registration is a lightweight reference; **the file is never copied, moved, modified, or deleted**.
2. **Executable** - Atlas locates `llama-server` from an explicit path you configure (persisted), then PATH lookup, then a few common install locations. **Atlas never downloads binaries automatically.**
3. **Launch** - a typed argument array is spawned directly (`shell:false` by construction): model path, loopback host `127.0.0.1`, an OS-assigned free port, and hardware-recommended settings (context size from SUPER++ 002's recommendation; GPU layers forced to CPU-only machines). No shell interpolation is ever involved, so paths with spaces are safe.
4. **Health gate** - startup waits until `/health` reports ready (model loading tolerated) within a bounded deadline; bind collisions retry on a fresh port a small number of times before failing cleanly.
5. **Use** - once running, the managed endpoint feeds the normal llama.cpp runtime/provider flow: the model appears in OpenCode's picker, and Benchmark/Readiness target it like any other instance.
6. **Own** - Stop/Restart act only on processes Atlas started (tracked by live child handle, never by persisted PID alone). Logs are captured into a bounded tail buffer viewable in `/local`. Normal OpenCode termination cleans up owned children; after a crash of Atlas itself the old process may survive but is never re-signalled - it shows as stale instead.

## Intelligent routing (experimental)

Atlas can choose the execution path for a request: **Auto**, **Local**, **Hybrid**, or **Cloud**. The mode is persisted (`/local` → Routing action) and applies wherever Atlas resolves a model; picking a concrete model manually always bypasses routing for that request.

Guarantees:

- **Local / `local_only` privacy is a hard wall.** If no capable local model exists, the request fails with "Cloud fallback is disabled by workspace policy" — cloud is never invoked.
- **Manual selection always wins.** Router bypassed, no reinterpretation.
- **Unknown cloud price is never free.** Candidates without pricing metadata are penalized and excluded from automatic escalation plans.
- **Cost caps are enforced**: candidates whose estimated cost exceeds `maxCloudCostPerRequest` are hard-rejected.
- **User cancellation never falls back.**

Decisions are deterministic and explainable: every result carries stable reason codes (`MODEL_WARM`, `MEASURED_FAST`, `CONTEXT_TOO_LARGE`, `COST_OVER_BUDGET`, …), scored alternatives, coarse confidence (high/medium/low from measured evidence quality), and a bounded fallback plan. Task classification uses request structure only — surface, token estimates, file count, tool/vision requirements — never an extra LLM call and never your prompt contents. Decisions/fallbacks emit `atlas.routing.decision` / `atlas.routing.fallback` events through the standard stream.

Evaluate or integrate via HTTP: `GET/POST /router/state|mode` and `POST /router/decide` (returns resolved provider/model identity; execution itself stays on OpenCode's normal provider path).

## Execution-time activation

When routing is opted in and a prompt carries no explicit model (no request override, no agent default, no session picker selection), the session execution path calls the router automatically: the selected candidate's identity becomes the user-message model, so streaming/tools/usage/errors flow through the normal provider stack. Safety rules at execution time:

- **Bounded pre-commit fallback**: if the run fails before meaningful output with a policy-eligible failure, Atlas advances through the decision's fallback plan — same candidate never twice, attempts capped, cloud spend tracked against caps.
- **No replay after commitment**: once meaningful text has streamed or any tool has executed, automatic fallback stops; the failure surfaces instead of silently restarting on another model.
- **Cancellation kills routing**: aborting a request disables further fallbacks and managed auto-start for that turn.
- **Managed auto-start** only when explicitly enabled (`allowManagedAutoStart`): cold registered GGUFs are started via the existing ownership lifecycle before provider invocation.

Fallback transitions emit `atlas.routing.fallback` events; the TUI surfaces them as concise toasts.

## Runtime events

Local AI publishes typed events through OpenCode's standard event stream (`/event`, `/global/event`):

| Event | Meaning |
| --- | --- |
| `localai.instance.lifecycle` | Managed instance transitions (`state` + transient `phase` such as `loading_model`, `health_wait`) with a per-artifact `generation` |
| `localai.instance.log` | Batched new stdout/stderr lines from an Atlas-owned process |
| `localai.health.changed` | Effective runtime health transitions only (never emitted on unchanged probes) |
| `localai.managed.artifact` | GGUF registered / removed / file missing / file restored |
| `localai.executable.changed` | llama-server path configuration or discovery result changed |
| `localai.benchmark.status` | started / completed / failed / cancelled with real metrics on completion |
| `localai.readiness.status` | started / `check_completed` (per probe) / completed / failed / cancelled |
| `localai.install.status` | Ollama download lifecycle: started / progress / verifying / completed / cancelled / failed |
| `localai.provider.changed` | A local model source became available or unavailable |

Correctness model: **snapshots are authoritative; events are immediacy.** Clients refetch the relevant snapshot on reconnect; missing an event never corrupts state. Each lifecycle event carries a monotonic per-artifact `generation` plus a unique `instanceID`, so stale events from a previous run are identifiable and droppable, and duplicate delivery is harmless.

Managed starts are non-blocking: the start request returns as soon as the process is spawned (identity + `starting` state), and progress arrives via events until the health gate resolves.

## How recommendations work

OpenCode detects your hardware (GPU vendor and VRAM, system RAM, Apple unified memory) and scores every catalog model against it per quantization variant. The final hierarchy is:

```text
hardware → model → quantization/context → runtime
```

Scoring combines fit, quality, speed (smoothly estimated from working-set size), practical context capacity, and agent readiness. Presets (`overall`, `coding`, `agent`, `speed`, `memory`, `context`) reweight these factors.

## Runtime selection

When a model is available through several runtimes, Atlas picks one:

- Your explicit preference (`Auto / Ollama / LM Studio / llama.cpp / MLX`, set in `/local`) wins whenever that runtime can actually serve the model.
- Otherwise **measured evidence decides**: real benchmark throughput and readiness results recorded per runtime.
- With no measurements anywhere, a transparent heuristic applies (install state + lifecycle completeness) and the UI says so - Atlas never invents speed numbers or hardcodes a runtime ranking.

## Model identity

The same logical model may exist on several runtimes. Atlas groups instances into logical identities using strict rules: matching quantization label, parameter count within 15%, and a shared family token. Uncertain matches are displayed separately instead of being merged. Benchmark and readiness records are stored per `[runtime][model artifact]`, so Qwen/Q6/Ollama and Qwen/Q6/llama.cpp never collide.

## Working set estimates

The recommended context for each variant is the largest standard context step whose full working set (weights + KV cache + runtime overhead) fits inside the GPU budget minus a 12% safety reserve. These are conservative estimates, always labeled as estimated.

## Offload

When a working set exceeds safe VRAM, part runs in system memory (none → partial → heavy → CPU dominant). Offloaded configurations are penalized heavily so a smaller model that fits usually outranks a larger one that spills.

## Estimated vs measured

Recommendations start from size-based estimates. Running **Benchmark** records real throughput against the exact runtime + model + quantization and replaces the estimate for that instance. Cross-runtime comparisons in `/local` show only measured values - unbenchmarked runtimes read "Not benchmarked".

## Downloads and cancellation

Before installing, OpenCode checks free disk space on the Ollama models directory (honoring `OLLAMA_MODELS`); if space cannot be determined the check is skipped rather than blocking you. Downloads stream progress into the TUI and can be cancelled mid-flight.

## Current limitations

- Registry pulls (install/remove) require Ollama; llama.cpp GGUFs and LM Studio/MLX models are referenced or managed externally by design.
- Managed llama.cpp requires you to already have `llama-server` installed; Atlas does not download binaries.
- Managed servers bind loopback only; LAN/remote serving is out of scope.
- Cleanup guarantees apply to processes Atlas started during the current session; after a hard OS kill, a previously spawned server may keep running (shown as stale, never signalled).
- MLX integration assumes an OpenAI-compatible MLX server is already running; no Python environment management.
- All pre-install numbers are estimates derived from parameter counts and public quantization profiles; only benchmark/readiness results are measured.
